## ADR-009 — Vendor deepseek4free at commit 4ae47bb; relax the curl-cffi pin

**Status:** Accepted

**Context:** Upstream `deepseek4free` ships no packaging metadata (`pyproject.toml`/`setup.py`), so `pip install git+...` is impossible. Its `requirements.txt` pins `curl-cffi==0.8.1b9`; that version has no wheel for Python 3.12+/3.14 on Windows and its sdist build fails because the prebuilt `libcurl-impersonate` release it downloads returns 404. The upstream repository has not been updated since 2025-02-09 (~18 months before M0), while the development machine runs Python 3.14.6.

**Decision:**

1. Vendor the upstream snapshot at commit `4ae47bbb144f33b0ba855af9d1b0206ea794e16c` under `vendor/deepseek4free/` (MIT license preserved; provenance in `vendor/deepseek4free/VENDOR_INFO.md`). Import via a `sys.path` seam in `app/backends/deepseek_web/_vendor.py`; nothing outside that backend package may import `dsk`.
2. Depend on modern `curl-cffi` (>=0.13; 0.16.0 verified). The vendored client only _warns_ on version mismatch, and everything it uses (`requests`-style API, `impersonate='chrome120'`, `iter_lines`) is present and verified in 0.16.0.
3. Apply exactly one minimal vendor patch (`[DSQG-VENDOR-PATCH]`): `pkg_resources` → `importlib.metadata` for a warning-only version check (`pkg_resources` no longer exists in setuptools >= 81 / stock 3.12+ venvs).

**Consequences:** Reproducible, reviewable upstream snapshot; private-API quirks stay isolated as required. The upstream pin's _behavioral_ assumptions (TLS fingerprint of 0.8.1b9) may differ subtly from 0.16.0's impersonation; the M0 live probe is the check for that. Any future vendor patch needs a marker + ADR note.

**Alternatives considered:** pip-from-git (impossible — no packaging); git submodule (heavier tooling, no patch capability); rewriting the client from scratch in M0 (scope violation — M0 is a spike using the existing integration).

## ADR-010 — Preserve unknown upstream delta types as UnknownDelta events

**Status:** Accepted

**Context:** `docs/ARCHITECTURE.md` suggests a fixed event inventory, but DeepSeek Web delta `type` values are private and can change (observed: `text`, `thinking`; plausible future/search types exist).

**Decision:** Unknown delta types are normalized into an explicit `UnknownDelta(kind, content)` event instead of being dropped. Callers may ignore them; the probe reports observed unknown kinds so fixtures/tests can be updated.

**Consequences:** Upstream drift becomes observable instead of silent. Small addition beyond the suggested inventory, documented in `app/backends/events.py`.

## ADR-011 — M0 surfaces backend failures as BackendFailure exceptions

**Status:** Accepted

**Context:** ARCHITECTURE.md lists `BackendError` among stream events, but M0's spike consumes the vendored synchronous generator, where mid-stream failures surface naturally as exceptions.

**Decision:** `DeepSeekWebBackend` raises `app.backends.errors.BackendFailure` (taxonomy category + retryability + optional status). The `BackendError` event class is still implemented and tested for inventory completeness; the event-vs-exception surface for async streaming is re-decided in M1/M3.

**Consequences:** Simple, testable M0. M1 must settle the canonical surface before the API layer exists.

## ADR-012 — Dual normalization entry points: raw SSE lines and reduced chunk dicts

**Status:** Accepted

**Context:** The vendored client's `_parse_chunk` reduces each SSE payload to `{content, type, finish_reason}` and discards everything else — including message/session identifiers needed later for `parent_message_id` threading (M4) and fixtures. The upstream README's threading example even relies on a `message_id` field that the vendored parser never emits.

**Decision:** The gateway implements its own faithful raw-line parser (`parse_sse_line` + `payload_to_events`) alongside normalization of the vendored reduced dicts (`chunk_dict_to_events`). The probe captures raw SSE lines through a non-invasive `_parse_chunk` wrapping seam so fixtures reflect the true wire format. Offline tests cover both paths.

**Consequences:** Fixtures and later canonical state can carry real identifiers; parser behavior matches or exceeds vendored tolerance (non-object JSON payloads tolerated, malformed JSON fatal — same as vendored). Slightly more M0 surface, bounded and tested.

## ADR-013 — Replace the vendored stream parser at runtime (WireSession)

**Status:** Accepted

**Context:** Live probing on 2026-08-14 proved DeepSeek Web changed its stream protocol: no more OpenAI-style `choices[].delta` payloads. The current wire format is an event + JSON-patch stream with sticky-path compression (`event: ready` ids, `{"p": path, "o": op, "v": value}` ops where `p`/`o` may be omitted after being set, terminal `response/status: FINISHED`). The vendored `_parse_chunk` matched zero lines of real traffic. The vendored _transport_ (HTTP request, headers, PoW, cookies, iteration loop, terminal break on `finish_reason == 'stop'`) still works.

**Decision:** Keep the vendored transport untouched; install a stateful adapter (`app/backends/deepseek_web/wire.py::WireSession`, one instance per stream turn) as the runtime `_parse_chunk` replacement via the existing instance-attribute seam (restored exactly after each turn). The adapter translates the current protocol into the backend chunk contract (`content`/`type`/`finish_reason` + `response_message_id`/`request_message_id`), mapping `FINISHED` → `finish_reason='stop'` so the vendored loop's terminal break fires. Legacy-format handling stays in `parse_sse_line`/`payload_to_events` for regression coverage of the generic parser.

**Consequences:** Minimal change surface; private-API transport stays isolated and replaceable; the adapter is fully unit-tested against sanitized live captures (parametrized over every capture, so future probes extend coverage automatically). Risk: further upstream protocol drift will surface as UPSTREAM_PROTOCOL failures or missing events — mitigated by raw-capture fixtures from every probe run.

**Alternatives considered:** patching vendored `api.py` (rejected — destroys clean diff against upstream and spreads private-API parsing across vendor code); reimplementing the whole HTTP request in gateway code (rejected for M0 — unnecessary duplication while vendored transport works; reconsider if transport also drifts).

## ADR-014 — Stable LLMBackend interface: ABC with typed value returns

**Status:** Accepted

**Context:** M1's core deliverable is a stable backend contract. ARCHITECTURE.md sketches it "conceptually similar to" a `typing.Protocol` with `create_session -> BackendSession`, `stream_turn -> Iterator[BackendEvent]`, `health_check -> BackendHealth`, noting exact signatures may evolve. The M0 spike returned bare `str`/`dict` and used a `chat_session_id` parameter.

**Decision:**

1. `app/backends/base.py` defines `LLMBackend` as an **ABC** (not a `Protocol`), with abstract `backend_type` (satisfied by a plain class attribute), `health_check() -> BackendHealth`, `create_session() -> BackendSession`, and `stream_turn(session_id, prompt, *, parent_message_id=None, thinking_enabled=False, search_enabled=False) -> Iterator[BackendEvent]`.
2. `BackendSession(session_id)` and `BackendHealth(backend_type, ready, details)` are frozen dataclasses named by ARCHITECTURE.md, replacing bare `str`/`dict` so later milestones can extend them without breaking the signature. `session_id` is opaque above the backend layer.
3. Backend-specific extras stay OUT of the contract: `DeepSeekWebBackend.stream_turn` keeps its `raw_sink` capture extension, documented as non-portable; `FakeBackend` implements exactly the interface.
4. Failures cross the interface as `BackendFailure` exceptions (reaffirming ADR-011 for the stable contract; `BackendError` events remain inventory-only until the async streaming surface is re-decided in M3).

**Consequences:** All layers above backends (API, compiler, tool emulation) program against `base.py` only; missing methods fail at instantiation; `isinstance(x, LLMBackend)` is meaningful. `DeepSeekWebBackend` renamed its first positional `chat_session_id` → `session_id` (all in-tree callers updated; probe and live tests included).

**Alternatives considered:** `typing.Protocol` (rejected — all backends live in this repo, so nominal subtyping gives fail-fast enforcement and explicit conformance without losing anything); keeping `str`/`dict` returns (rejected — no extension headroom, weaker docs/tests).

## ADR-015 — Configuration boundary: pydantic v2 + SecretStr + factory registry

**Status:** Accepted

**Context:** M1 requires a configuration boundary: one place where environment settings become gateway objects, without ever leaking the DeepSeek token (credentials rule). The default architecture mandates pydantic v2.

**Decision:**

1. `app/config.py` is the single env→settings→backend path: `GatewaySettings.from_env(env=None)` parses `GATEWAY_BACKEND` (`deepseek_web` default, or `fake`), `DEEPSEEK_AUTH_TOKEN` (required for `deepseek_web`), and optional `DSQG_COOKIES_FILE`. The token is stored as `pydantic.SecretStr` so masking in `repr`/JSON dumps is by construction (and tested). `ConfigError` (a `ValueError`) names variables only, never values.
2. `build_backend(settings) -> LLMBackend` is the backend selection registry. It imports backend implementations **lazily**, so `GATEWAY_BACKEND=fake` development and tests never pull the vendored private-API stack.
3. `FakeBackend` is a first-class selectable backend for credential-free development of later milestones (M2/M3), not only a test fixture.

**Consequences:** New backends register in exactly one function; secret hygiene is mechanical + regression-tested; settings objects are immutable. Adds `pydantic>=2` to runtime dependencies (already required by the default architecture).

**Alternatives considered:** `pydantic-settings` (rejected for now — one extra dependency for a single injectable `from_env` classmethod; reconsider if settings grow); plain dataclasses with manual masking (rejected — hand-rolled secret masking is exactly the bug class SecretStr prevents).

## ADR-016 — Import-boundary guard: AST scan with a documented tests exemption

**Status:** Accepted

**Context:** AGENTS.md/QWEN.md require that nothing outside `app/backends/deepseek_web` imports the vendored `dsk` namespace. M0 already has intentional `dsk` imports in two test modules (`test_errors.py`, `test_backend_offline.py`) — they import vendored exception classes to prove the taxonomy mapping itself.

**Decision:** `tests/test_import_boundary.py` statically scans `app/` and `scripts/` (AST-based, so lazy/local imports inside functions are caught too) and fails on any `dsk` import outside `app/backends/deepseek_web/`. `tests/` is exempt by documented design. The guard includes a self-test of its detector so refactors cannot silently neuter it.

**Consequences:** The isolation rule is mechanically enforced on every default test run instead of relying on review. Any future exemption needs an ADR note.

## ADR-017 — Gateway API auth: secure-by-default bearer key with explicit dev opt-out

**Status:** Accepted

**Context:** API_CONTRACT.md mandates `Authorization: Bearer <GATEWAY_API_KEY>` for the OpenAI surface, distinct from the DeepSeek token, and says authentication "may be configurable" for development but "secure-by-default behavior is preferred". The gateway binds locally, but a port on 127.0.0.1 is still reachable by every local process (and by LAN peers if rebound), and it proxies a valuable DeepSeek session.

**Decision:**

1. `/v1/models` and `/v1/chat/completions` require `Authorization: Bearer <DEEPSEEK_GATEWAY_API_KEY>`; comparison uses `hmac.compare_digest`; the bearer scheme prefix is case-insensitive. Failures answer 401 with OpenAI-style `code: "invalid_api_key"` (same for missing header, wrong scheme, wrong key — no enumeration hints).
2. When no key is configured the gateway **refuses to serve**: 503 `code: "GATEWAY_API_KEY_NOT_CONFIGURED"` on `/v1/*`. The only escape hatch is the explicit opt-in `GATEWAY_ALLOW_NO_AUTH=1` (development convenience, documented as such in `.env.example`).
3. `GET /health` stays unauthenticated: it reports only liveness, version, backend type/status — never secrets (contract rule "Do not expose secrets").
4. The gateway key lives in `GatewaySettings.gateway_api_key` as `SecretStr` (ADR-015), so it inherits masking in repr/dumps.

**Consequences:** A fresh checkout cannot accidentally expose an open proxying endpoint; misconfiguration fails loudly instead of silently open. Qwen Code wiring (M5) will set the key in the provider config. The constant-time compare is cheap insurance even for a local key.

**Alternatives considered:** open-by-default with optional key (rejected — inverts the contract's stated preference and the threat of a silently open proxy); per-request signed tokens/JWT (rejected — no multi-user model exists; a shared local key is the right weight class).

## ADR-018 — M2 HTTP surface: non-stream only, explicit honest rejections, lenient parsing

**Status:** Accepted

**Context:** M2's exit criterion is "curl/OpenAI-compatible client can complete plain chat". Qwen Code source verification (docs/UPSTREAM_NOTES.md) fixed several constraints: the client always sends `stream` explicitly (agent turns stream=true), may send non-standard request fields (`reasoning_effort`, `enable_thinking`, ...), never retries 400 but retries 429/5xx, and sends `max_tokens` on every turn.

**Decision:**

1. `POST /v1/chat/completions` implements NON-STREAMING plain chat only: `system`/`user`/`assistant` text messages compiled by `app/prompt_compiler.py` into one deterministic backend prompt; a fresh backend session per request (stateless; canonical conversation state is M4).
2. Not-yet-implemented capabilities are rejected loudly and specifically instead of silently degraded: `stream: true` → 501 `STREAMING_NOT_YET_SUPPORTED` (points at M3); `tools`/`tool_choice` → 400 `TOOLS_NOT_YET_SUPPORTED` (points at M6); `role=tool`, assistant `tool_calls`, or null-content assistant messages → 400 `UNSUPPORTED_MESSAGE` (points at M6). 501 was chosen for streaming despite the client retrying 5xx (retries are bounded; the status is semantically honest; by the time Qwen Code is wired in M5, M3 streaming exists, so this path is transient).
3. Request parsing is lenient: request models use pydantic `extra="allow"`, so unknown fields (sampling knobs, vendor extras) are accepted and ignored — documented in `app/openai_types.py`, per the contract's "accept but initially may ignore" rule. Sampling parameters are NOT enforced in M2 (the backend takes a single prompt; there is nothing to map them onto).
4. `model` must equal the configured alias (`GATEWAY_MODEL_ID`, default `deepseek-web`) else 404 `model_not_found`. Empty/missing `messages`/`model` → 422 via pydantic.
5. `BackendFailure` maps to OpenAI-style errors via `app/error_mapping.py` (status per contract table, `code` = stable category value). `BackendError` events are defensively converted to failures too.
6. Handlers are plain `def` (synchronous); Starlette's threadpool isolates the blocking backend from the event loop. `finish_reason` mapping: `length` → `length`, everything else → `stop` (`tool_calls` arrives in M6).

**Consequences:** The M2 surface is fully testable offline (TestClient + FakeBackend), every unimplemented feature announces its milestone, and lenient parsing means Qwen Code's real request bodies will not 422 on contact. Session-per-request spends one upstream session (and its PoW) per call until M4 adds reuse — an accepted interim cost.

**Alternatives considered:** silently returning empty `tool_calls`/stream responses (rejected — would corrupt client state invisibly); strict request validation (rejected — the verified client sends non-standard fields); holding one long-lived backend session in the server (rejected — belongs to M4 canonical state, not the M2 adapter).

## ADR-019 — M3 streaming surface: single translator, primed HTTP-status errors, honest mid-stream failure

**Status:** Accepted

**Context:** M3's exit criterion is "incremental normal text works and raw DeepSeek SSE never leaks". ADR-011/014 deferred the `BackendError`-event-vs-exception question to this milestone ("re-decided at M3 async streaming"). Qwen source verification fixed the client-side expectations: explicit `stream:true` + `stream_options.include_usage` on agent turns, chunk accumulation by standard OpenAI rules, retries keyed off HTTP status (400 never retried; 429/5xx retried), missing usage chunk tolerated.

**Decision:**

1. `app/streaming.py` is the ONLY translator between normalized events and the public SSE wire. Rendering rules: `MessageStarted` → role chunk `{"role":"assistant","content":""}` (role is force-injected into the first rendered chunk if the backend skips `MessageStarted`); `TextDelta` → `{"content": ...}`; `MessageFinished` → empty delta + mapped finish reason (`length`→`length`, else `stop`); then `data: [DONE]`. All chunks share one `chatcmpl_local_*` id, `created`, `model`.
2. **Nothing vendor-internal crosses the wire.** `ReasoningDelta`, `BackendMessageId`, `UnknownDelta` render to NOTHING in M3 (reasoning surfacing, if ever, is a later explicit decision). Upstream JSON-patch framing, ids and control events never appear in the public stream — this is the mechanical guarantee behind the exit criterion.
3. **Errors before the first byte are HTTP statuses.** The route pulls the FIRST backend event synchronously ("priming") before returning the `StreamingResponse`, so `BackendFailure` (or a primed `BackendError` event) still answers 4xx/5xx with the OpenAI error body — preserving the client's status-keyed retry semantics.
4. **Errors after headers are committed are in-stream.** A mid-stream `BackendFailure` emits `data: {"error": {message, type, code}}` and closes WITHOUT `[DONE]` (the openai SDK raises on the error event; a missing `[DONE]` unambiguously marks an incomplete stream). Re-decision per ADR-011/014: exceptions remain the canonical cross-boundary failure surface; `BackendError` events are defensively normalized into the same failure path on both sides of priming, but stay inventory-only types.
5. **No usage chunk.** DeepSeek Web exposes no token counts; the verified client tolerates absence even with `include_usage:true`. Emitting fabricated zeros would violate "never silently pretend".
6. **Threading/disconnect.** The blocking backend iterator is consumed via `starlette.concurrency.iterate_in_threadpool`; handlers stay sync `def`. On client disconnect Starlette closes the async generator; the in-flight upstream turn runs to completion in the threadpool (stateless session policy — nothing to roll back). Yielded exception instances are defensively raised. Cancellation of in-flight upstream work is M9 scope.

**Consequences:** Streaming is fully testable offline (translator units + TestClient `stream()`); raw-leakage is guarded by construction and by explicit no-leak tests; error semantics match what the Qwen Code client actually does with statuses. Degenerate turns (empty stream) still emit a well-formed role + finish + `[DONE]` sequence.

**Alternatives considered:** emitting `[DONE]` after a mid-stream error (rejected — `[DONE]` must mean "completed successfully"); fabricating a usage chunk (rejected — dishonest data); async route handlers (rejected — the backend is blocking; threadpool isolation is the established pattern); buffering the whole turn then emitting one chunk (rejected — defeats incremental delivery).

## ADR-020 — M4 canonical conversation state: bounded in-memory store, history-prefix resolution, commit-on-finish

**Status:** Accepted

**Context:** M4's exit criterion is "multi-turn plain chat is correct and locally reconstructable". ARCHITECTURE.md mandates a conversation manager holding local canonical state (`conversation_id`, `backend_type`, `backend_account_id`, `backend_session_id`, `backend_parent_message_id`, timestamps, `status`, normalized or reconstructable history), declares a backend remote session "an optimization/state link, not the sole source of truth", and requires later failover to rebuild a remote session from canonical state. It also demands the storage decision be recorded here: persistent full-content storage vs "bounded in-memory state for v1". Inputs: the Qwen Code client re-sends its full message history on every request (source verification, docs/UPSTREAM_NOTES.md); DeepSeek Web keeps its own server-side context keyed by session + `parent_message_id`, and the threading id is already exposed (`event: ready` → `response_message_id`; `wire.py` surfaces it and `chunk_dict_to_events` emits it as `BackendMessageId`, both since M0); the master prompt forbids persisting raw prompts/tool output by default.

**Decision:**

1. `app/conversation.py` owns canonical state. `CanonicalMessage` (role, content, tool_calls, tool_call_id, name) and `CanonicalToolCall` (id, function name, arguments JSON string) are frozen dataclasses — the representation is tool-history-capable now and populated from M6 on. `Conversation` carries every ARCHITECTURE.md field (`backend_account_id` stays `None` until multi-account exists) plus plain-dict `to_dict()`/`from_dict()` — the "reconstructable representation" (JSON-serializable, ready for later persistence/failover).
2. **Storage: bounded in-memory only (the v1 decision ARCHITECTURE.md asked to record).** `ConversationStore` keeps at most `max_conversations` (default 256) conversations, evicting the least-recently-updated first, guarded by a `threading.Lock`. Nothing is written to disk: prompts and history live only in RAM and die with the process — the privacy default ("never persist raw prompts by default"). SQLite (ADR-007) remains the intended persistence layer; it is reconsidered together with multi-account (M10), where `accounts`/`conversations` tables first pay rent. After a restart, the client's own re-sent history IS the reconstruction path.
3. **Conversation resolution = longest strict prefix match on canonical history.** Incoming messages are normalized to canonical form; a stored conversation matches when its history equals a leading slice of the incoming history and is strictly shorter; the longest match wins and the trailing delta (new messages) is returned. Equal histories (duplicate re-send of a completed turn) and divergent histories do not match — the request falls back to a NEW conversation compiled from its own full history. No conversation header is introduced: the contract says an internal header "must not be required" and "prefer correctness from the request's canonical message history".
4. **Delta vs rebuild.** Matched conversation with a live `backend_session_id` → only the delta messages are compiled into the prompt (the upstream session already holds prior context) and the stored `backend_parent_message_id` is passed as `parent_message_id`. New conversation or invalidated link → a fresh backend session is created and the request's FULL history is compiled (rebuild). Canonical state is therefore always sufficient to rebuild a remote session — ARCHITECTURE.md's failover requirement — without any retry loop in M4.
5. **Commit-on-finish; failure invalidates.** Canonical history advances only when a turn completes with `MessageFinished`: history := incoming + assistant reply; `backend_parent_message_id` := last observed `BackendMessageId`. Any `BackendFailure` before that leaves history untouched and clears the conversation's backend link (session + parent), so the next request rebuilds from canonical history on a fresh session. Partial assistant text is never stored.
6. **Parent threading.** The server captures `BackendMessageId` events (emitted by the DeepSeek backend from the ready frame; scriptable in `FakeBackend`); the last id of turn N becomes turn N+1's `parent_message_id` on the same session — the convention observed live in M0.

**Consequences:** Multi-turn plain chat reuses ONE upstream session and threads parent ids (verified offline via `FakeBackend` call recording); state is locally reconstructable (dict round-trip tests inject rebuilt conversations into a fresh store and continue the same backend session); a restart loses in-memory state but stays correct because every request carries its own history; eviction of idle conversations is self-healing (their next request rebuilds); concurrent duplicate requests may create duplicate conversation rows (accepted for a single-user local gateway; the store's lock only guarantees internal consistency).

**Alternatives considered:** SQLite persistence now (rejected for v1 — writes prompt content to disk against the privacy default and adds nothing until multi-account/failover milestones); re-compiling the full history every turn regardless of session state (rejected — duplicates context the upstream session already holds); a required/optional conversation-id header (rejected as a requirement — the contract forbids requiring it and history inference meets the M4 exit); automatic rebuild-and-retry within the failing turn (rejected in M4 — rebuild-on-next-request is simpler and client retry semantics already re-drive failed turns; revisit with M9/M10 failover).

## ADR-021 — M5 real Qwen Code wire compatibility: tolerate tools, opt-in diagnostic capture, source-verified fixtures

**Status:** Accepted (partially supersedes ADR-018's `tools`/`tool_choice` rejection)

**Context:** M5's exit is "real Qwen Code can use the gateway for plain chat; the exact current agent request/history format is documented and covered by tests". Source verification (docs/UPSTREAM_NOTES.md, Qwen Code v0.21.11 commit a669957f) established that EVERY agent turn carries a non-empty `tools[]` plus `stream: true` + `stream_options.include_usage`. ADR-018 answered tools with `400 TOOLS_NOT_YET_SUPPORTED` — correct as an M2/M3/M4 placeholder, but it makes the M5 exit unreachable: a real Qwen Code could not complete even plain chat against the gateway. API_CONTRACT.md sanctions three treatments for unsupported parameters: map it, explicitly ignore it with documented behavior, or reject if semantic correctness requires rejection. No live capture was available (no user test session this milestone), so the "actual tools[] schema sent by Qwen Code" had to be fixtured from source verification instead.

**Decision:**

1. **`tools`/`tool_choice` are ACCEPTED AND IGNORED from M5 on (both response modes).** The gateway answers plain text with `finish_reason: stop`; it never echoes tools and never fabricates `tool_calls` — dishonest tool output would be worse than none. `tool_choice` only ever arrives as `'required'`/`'none'` from Qwen Code (never `'auto'`); both are tolerated. This is the "explicitly ignore with documented behavior" option, documented here, in API_CONTRACT.md, in docs/QWEN_CODE_INTEGRATION.md, and in server comments. M6 replaces "ignore" with real prompt-emulated tool calling (ADR-006) and will honor `tool_choice: required` semantically.
2. **Tool-shaped HISTORY messages stay `400 UNSUPPORTED_MESSAGE` until M6.** Assistant `tool_calls`, `role=tool`, and null-content assistant messages cannot occur in an M5 plain-chat session anyway — the gateway never emits tool calls, so Qwen Code can never hold tool history against it. The exact shapes are fixtured now (`tests/fixtures/qwen_code_wire/tool_history_turn.json`) with a test pinning the deterministic 400, so M6 has a locked target.
3. **Opt-in diagnostic capture layer** (`app/diagnostics.py`, `GATEWAY_DIAGNOSTICS_DIR`): when configured, every authenticated `/v1/chat/completions` request is appended to `<dir>/requests.jsonl` BEFORE validation (rejected shapes are exactly what wire fixtures need). Sanitization: the Authorization header VALUE is never written (only present/absent); only content-type and user-agent header values are kept. Request bodies ARE written — that is the purpose of the layer — so the directory must be private; capture is strictly opt-in, keeping the "never persist raw prompts by default" non-negotiable intact. Capture is best-effort: failures log and never break request handling.
4. **Wire fixtures are source-verified, not captured.** `tests/fixtures/qwen_code_wire/*.json` encode the verified agent request/history format (agent turn with tools + include_usage; side query with explicit `stream:false`; tool-loop history; non-standard extras like `reasoning_effort`/`enable_thinking`/`chat_template_kwargs`/`metadata`/`cache_control`), with provenance in the fixture README. When a real Qwen Code connects with capture enabled, the JSONL records are the comparison source for drift.
5. **SDK-driven wire-compat tests stand in for the live connection.** `tests/test_m5_sdk_compat.py` drives a real uvicorn gateway through the real openai Python SDK (models.list, non-stream, streaming with `stream_options`, tools tolerance, extra_body) over actual HTTP — the closest offline proof that an OpenAI client library parses every byte the gateway emits. The live step (user connects a real Qwen Code install per docs/QWEN_CODE_INTEGRATION.md) remains the final acceptance and is prepared turnkey.

**Consequences:** A real Qwen Code can complete plain chat today (agent turns no longer 400); honest behavior is preserved (no fake usage, no fake tool_calls, no fake parameter enforcement — the API_CONTRACT "never silently pretend" rule); the wire format is regression-covered offline by fixtures + SDK tests; the diagnostic layer doubles as the live-capture path that converts source-verified fixtures into traffic-verified ones. `TOOLS_NOT_YET_SUPPORTED` is gone; `UNSUPPORTED_MESSAGE` remains the only M5-era tool-related 400.

**Alternatives considered:** keeping the tools 400 until M6 (rejected — makes the M5 exit unreachable; Qwen Code agent turns ALWAYS send tools); faking a `tool_calls` response or a usage chunk to look more complete (rejected — fabricated structured output would send Qwen Code down a tool loop the gateway cannot serve, violating "never silently pretend"); raw-byte request capture via middleware (rejected for M5 — parsed-body capture already covers the semantic wire shape; revisit only if real captures show fidelity gaps); capturing unauthenticated requests (rejected — auth runs before the handler, keeping capture scoped to legitimate traffic is simpler and privacy-friendlier).

## ADR-022 — Repository-root `.env` loading for live runs

**Status:** Accepted (post-M5 live-acceptance enabler)

**Context:** The M5 live-acceptance step asks the user to run the gateway with a real token. Per-variable `set` commands in a terminal are error-prone and must be repeated for every new shell; the user asked to configure via `.env`. `.env` is already gitignored and `.env.example` documents every variable, but nothing loaded the file (`from_env` reads only `os.environ`).

**Decision:**

1. `app/config.py::load_env_file(path=None, env=None)` merges a `.env` file's `KEY=VALUE` pairs under `env` (default `os.environ`) and returns a NEW mapping; `app/main.py` calls `GatewaySettings.from_env(load_env_file())`. Parsing is deliberately minimal: one pair per line, `#` comments and blanks ignored, leading `export ` tolerated, one pair of surrounding quotes stripped, no `=` → skipped, no variable expansion.
2. **Real environment variables always win** (standard dotenv `override=False` semantics) — an explicit `set`/`export` is the escape hatch and the file can never shadow it.
3. The default path is the repository-root `.env` resolved from the `app` package location (`Path(__file__).resolve().parent.parent / ".env"`), so startup works from any working directory. A missing file is a no-op, not an error.
4. Loading happens ONLY in `app/main.py` (the runtime entry). `GatewaySettings.from_env()` itself is unchanged — tests and embedders keep full control of their environment and a local `.env` can never leak into the test suite.
5. No new dependency: a ~30-line parser instead of `python-dotenv` (the needed subset is tiny; dependency budget stays lean per ADR-015 spirit).

**Consequences:** `python -m app.main` after copying `.env.example` → `.env` and filling in the token is the whole live-run story; documented in `.env.example`, `docs/QWEN_CODE_INTEGRATION.md`, and PROGRESS. Covered by `tests/test_config.py::TestLoadEnvFile` (parsing, precedence, missing file, from_env integration).

**Alternatives considered:** `python-dotenv` dependency (rejected — only KEY=VALUE is needed); loading inside `from_env()` when `env is None` (rejected — a local `.env` would silently alter test behavior and any embedder's defaults); cwd-relative `.env` only (rejected — breaks when the gateway is started from another directory).

## ADR-023 — Prompt-emulated tool calling (M6)

**Status:** Accepted (supersedes the ADR-021 invariant "tools never reach the backend prompt"; M6 live-verified)

**Context:** DeepSeek Web has no native function-calling API; Qwen Code agent turns ALWAYS send `tools[]` and expect structured `tool_calls` output (M5 fixtures). M6's exit is one emulated tool call: the gateway teaches the model a control-envelope protocol in the prompt, parses the model's output for it, and re-emits it as OpenAI-shaped `tool_calls` — while keeping every M2–M5 path byte-identical when no tools are active. The hard constraints from docs/TOOL_CALLING_PROTOCOL.md: never fabricate a tool call, never parse anything but the current inference output, and honest plain text on any malformed envelope.

**Decision:**

1. **Lenient normalization in, strict parsing out.** `normalize_tools` (app/tools.py) accepts the messy real-world `tools[]` — skips non-function entries, malformed shapes, and names failing `^[A-Za-z0-9_-]{1,64}$`; first-wins on duplicates; empty result = no tools — so Qwen Code's payloads never 400 on shape alone. The `EnvelopeParser` (app/tool_envelope.py) is the opposite: an envelope is honored ONLY when the JSON object parses, `name` is a string naming a declared tool, and `arguments` pass `arguments_compatible` against the tool's schema (required keys present, shallow JSON-type match, bool never satisfies integer/number). Any failure — unknown tool, bad JSON, non-object payload, missing required argument, truncated envelope at end of stream — flushes the raw envelope text as honest plain content. No fabrication, ever. Bounded model repair (re-prompting once) is deliberately M7, not M6.
2. **Deterministic `[available tools]` instruction block**, built by `build_tool_instructions(tools, required=...)` and appended AFTER the compiled message history, once per request (identical for delta and full prompts). With `tool_choice="required"` it says "You MUST request exactly one tool call now"; otherwise "request one only when your next step needs it". One tool call per model turn — parallel calls stay Deferred per the ROADMAP.
3. **Injection boundary: only current inference output is parsed.** The parser wraps the backend event stream (`_tool_aware_events` in app/server.py), never the compiled history. Tool results and user messages containing sentinel text compile as data blocks and are never scanned. The streaming parser holds back candidate sentinel prefixes across chunk boundaries, so an envelope split mid-stream is either emitted whole or flushed whole — a partial envelope is never streamed.
4. **Canonical compact arguments both directions.** `normalize_arguments_json` renders arguments as compact JSON (`ensure_ascii=False`) on BOTH the emitted `tool_calls` and the re-sent assistant history, so a round trip through Qwen Code compares structurally equal regardless of whitespace or key-order differences in what the client sends back.
5. **Tool-call ids are gateway-minted: `call_dsqg_<uuid4.hex>`.** They cannot alias backend message ids; persistent cross-request id mapping is M7 scope, as is repeated tool-result/model cycling.
6. **Wire-shape discipline.** Responses serialize via `model_dump(mode="json", exclude_none=True)` inside a `JSONResponse`: plain responses keep the exact M2 shape (no `tool_calls: null`), tool turns carry `choices[0].message.tool_calls` and omit null `content`; streaming emits one opener chunk (`index: 0`, id, name, empty arguments — plus `role` if not yet sent) then one arguments chunk, and `finish_reason` is `"tool_calls"` whenever a call was emitted (overriding the backend reason). Assistant turns with tool calls store `content=None`; null content without tool calls is still a 400 as in M2.
7. **`tool_choice` semantics:** `"none"` fully disables tools (no instructions, no parser — envelope text in the answer streams as plain content); `"required"` adds the MUST wording. `tools_enabled = bool(normalized_tools) and tool_choice != "none"`.
8. **History compilation gains tool shapes.** `role=tool` requires a non-empty `tool_call_id` and compiles to `[tool result]` blocks; assistant `tool_calls` compile to `[assistant tool call]` blocks (plus the text content block when present). `compile_canonical_to_prompt` resolves a result's tool name from (a) calls seen earlier in the compiled sequence, then (b) a `known_tool_names` seed built from the request's FULL canonical history (delta prompts exclude the assistant call itself but must still name its result), then (c) `message.name`, else `"unknown"`.

**Consequences:** The M6 live smoke passed FIRST TRY against the real DeepSeek backend: streaming turn 1 finished `tool_calls` with `call_dsqg_57e118c6…` / `list_project_files` / `{"path":"."}` and zero content chars; the non-stream round trip (re-sending that exact tool history) finished `stop` with content "README.md" — proof the model follows the custom envelope protocol and that the canonical round trip works live. Full suite 370 passed / 3 deselected, with `parser=None` passthrough keeping every M2–M5 path byte-identical when tools are disabled or absent. Remaining M6 limits (all M7 by design): one call per turn, no bounded repair, no persistent id mapping, no repeated cycles.

**Alternatives considered:** native-style function calling via a separate model or proxy (rejected — the whole point is the Web backend); parsing the envelope out of compiled history too (rejected — turns tool results and user quotes into an injection vector, violating the protocol's data/tool-decision boundary); silently dropping invalid envelopes (rejected — honest plain text preserves the "never silently pretend" rule and keeps failures debuggable); emitting `tool_calls` with best-effort arguments despite schema mismatch (rejected — fabricated calls send Qwen Code into loops the gateway cannot serve); a union route annotation `ChatCompletionResponse | JSONResponse` (rejected — breaks FastAPI route registration; the route returns `JSONResponse` instances, which FastAPI passes through untouched, with the annotation staying `ChatCompletionResponse`).

## ADR-024 — Compacted tool instruction block for the upstream prompt budget (post-M6 hotfix)

**Status:** Accepted (live-verified against DeepSeek Web)

**Context:** The first real Qwen Code agent turn through the gateway stalled for over six minutes until the user interrupted it. Diagnostics capture + offline replay proved why: Qwen Code's harness ships ~69 tools, and `build_tool_instructions` rendered them VERBATIM — full multi-paragraph descriptions (62,375 chars) plus full JSON schemas including every property description (40,610 chars) — inflating the `[available tools]` block to 106,333 chars and the compiled prompt to 165,262 chars. DeepSeek Web handled the ~59KB history-only part in seconds (M5 live evidence) but stalled on the 165KB total; Qwen Code timed out (~6 min) and auto-retried. The gateway pipeline itself was proven clean: replaying the captured request through the real app with a FakeBackend returned 200 + `[DONE]` in 0.112 s.

**Decision:** `build_tool_instructions` renders a COMPACTED block (app/tools.py):

1. **Descriptions reduce to the first non-empty line, capped at 150 chars** (`_DESCRIPTION_MAX_CHARS`) with a trailing ellipsis when truncated. The first line of Qwen Code's tool descriptions carries the selection signal; the remaining paragraphs are usage prose the model does not need to pick and call a tool.
2. **`description` keys are stripped from rendered schemas at every nesting depth** (`_strip_schema_descriptions`, a deep copy — the caller's schema object is never mutated). Every validation-relevant member survives: type / properties / required / items / enum / default.
3. **Validation is unchanged.** The envelope parser still checks emitted arguments against the FULL un-compacted schema from `normalize_tools`; compaction only affects what the upstream model sees, never what the gateway accepts.

**Consequences:** The same captured 69-tool turn now compiles to 25,727 instruction chars (−76%) and 84,656 total prompt chars (−49%). Live verification against the real backend: first token in 2.6 s (previously >6 min stall), coherent answer. The envelope protocol still works live after compaction (probe turn finished `tool_calls` with correct name + arguments). Suite 376 passed at this step. Trade-off accepted: the model sees less prose per tool; if tool selection quality ever degrades, the cap is one constant and the stripping is one function — both trivially tunable without wire changes.

**Alternatives considered:** truncating the tool LIST (rejected — Qwen Code expects every declared tool to be callable; hiding tools invites unknown-name envelopes); aggressive schema stripping beyond descriptions (rejected — enum/default/items are selection signals too, and the description keys alone accounted for the bulk); moving tool descriptions to a retrieval step (rejected — out of scope, adds latency and a new failure mode for a problem a rendering rule solves); doing nothing and hoping DeepSeek catches up (rejected — the user-visible symptom is a >6-minute hang).

## ADR-025 — Serialize `parent_message_id` as an upstream number (post-M6 hotfix)

**Status:** Accepted (live-verified against DeepSeek Web)

**Context:** The same user session also showed a NEW DeepSeek chat appearing with the full prompt re-sent after turn 1. Forensics: capture records showed the turn-2 request failing within ~1 s and the client re-sending a byte-identical body; the retry took the M4 rebuild path (fresh backend session + full history) — by design self-heal, but triggered every time. A wire-level live probe reproduced the first-attempt failure and captured the upstream 422 body: `Failed to deserialize the JSON body into the target type: parent_message_id: invalid type: string "2", expected u32`. DeepSeek Web requires `parent_message_id` as a JSON NUMBER; the vendored client serializes whatever it is given, and the gateway's conversation store holds ids as strings — so EVERY session-reuse delta turn 422'd and the M4 delta strategy (ADR-020) never actually worked live until now.

**Decision:** `DeepSeekWebBackend.stream_turn` converts a numeric-string `parent_message_id` to `int` at the adapter boundary before calling the vendored client (`str.isdigit()` guard; non-numeric strings and None pass through unchanged). The stable `LLMBackend` interface, the conversation store, and all canonical state keep their string representation — the conversion is an upstream wire-format concern and lives exactly where upstream-specific concerns belong (the backend adapter, per AGENTS.md). The vendored code is untouched.

**Consequences:** Live verification: turn 2 with tool history now succeeds ON THE REUSE PATH (1.1–1.5 s, finish `stop`, context-aware answer "README.md") — no rebuild, no duplicate chat in the user's DeepSeek account. The earlier 422 body is preserved as a code comment at the conversion site. Suite 379 passed at this step. The M4 delta+parent strategy is now live-verified for the first time; the duplicate-session symptom the user reported is explained end-to-end (client retry after 422 → rebuild path → new visible chat + full prompt).

**Alternatives considered:** patching the vendored client's `json_data` construction (rejected — vendor churn; the adapter boundary exists precisely for this); storing ids as ints in the conversation store (rejected — leaks an upstream serialization detail into stable, backend-agnostic state; other backends may have non-numeric ids); dropping `parent_message_id` and always rebuilding (rejected — the rebuild path compiles the FULL history every turn: that is exactly the prompt-size regression ADR-024 fights, and it creates a new DeepSeek chat per turn).

## ADR-026 — Emit the initial snapshot's content in the wire adapter (post-M6 hotfix)

**Status:** Accepted (live-verified against DeepSeek Web)

**Context:** The delta-turn probe answers were missing their first tokens ("README.md" arrived as ".md" once, "The first file…" as " first file…"). Raw upstream capture showed why: DeepSeek Web's initial `{"v": {"response": {...}}}` snapshot event can already carry generated text (`"content": "The"`, status WIP) BEFORE any `response/content` APPEND op. The adapter (wire.py) extracted only `message_id` from that snapshot and discarded the content — silently dropping the first chunk of every affected answer.

**Decision:** The snapshot branch of `WireSession.adapt` now emits non-empty `content` (type `text`) — or `thinking_content` (type `thinking`) when content is empty — as part of the snapshot chunk, alongside the `response_message_id`. `content` wins when both are present (the one-chunk-per-line contract cannot carry both). Empty snapshots behave exactly as before.

**Consequences:** Live re-verification: the delta turn's answer arrives complete ("README.md", 9/9 chars). The M0 protocol notes in wire.py's docstring record the snapshot-content fact. Suite 382 passed. The bug had been invisible to all offline fixtures (the M0 live captures happened to start with empty snapshots) — which is why the fix ships with synthetic snapshot-content tests in tests/test_wire.py.

**Alternatives considered:** buffering the snapshot and merging it with the first APPEND (rejected — adds state and latency for a case the chunk contract already handles); treating snapshot content as authoritative and ignoring APPENDs (rejected — APPENDs carry the rest of the stream).

## ADR-027 — Serialize all DeepSeekWebBackend calls (post-M6 hotfix)

**Status:** Accepted (live-verified against DeepSeek Web)

**Context:** The Rust panic the user reported next to the gateway (`thread '<unnamed>' panicked at crates\unwinder\src\stackwalk.rs:234:9: 0x... > 0x...`) was NOT an external component — forensic string-scanning located the exact panic path inside `.venv\Lib\site-packages\wasmtime\win32-x86_64\_wasmtime.dll` (adjacent strings: `wasmtime_internal_unwinder::stackwalk`, "contiguous sequence of Wasm frames", `trampoline_fp = 0x`). The vendored dsk client solves DeepSeek's per-request PoW challenge in a WebAssembly module (`dsk/pow.py`) and shares ONE wasmtime Engine/Store/Instance across the whole process. Qwen Code sends its side query and agent turn in the SAME second (capture records 12+13, 14+15); FastAPI serves sync handlers on a threadpool, so two threads solved PoW concurrently on the shared Store — corrupting wasm state until wasmtime's unwinder assertion failed. The panic aborts the interpreter: `python.exe.*.dmp` crash dumps sit in `%LOCALAPPDATA%\CrashDumps` at the exact timestamps of the failed request pairs (23:59:26, 00:05:48, …). The same concurrency also corrupts the per-turn `_parse_chunk` seam that `stream_turn` installs on the shared client instance. This crash — not only the ADR-025 422 — contributed to the duplicate-session symptom (client retries after a dead gateway hit the rebuild path).

**Decision:** `DeepSeekWebBackend` gains a process-wide call gate — `self._call_gate = threading.Semaphore(1)` — held around `create_session` and around `stream_turn` for the turn's WHOLE lifetime (across yields). Every backend call is thus serialized; concurrent OpenAI requests queue at the adapter boundary instead of racing inside the vendored client. A Semaphore(1) rather than a threading.Lock because one streamed turn is iterated by several threads over its lifetime (priming thread, threadpool hops, aclose on disconnect) and the gate must release on whichever thread finishes it — a Lock would raise on cross-thread release. The stable `LLMBackend` interface is unchanged; serialization is an adapter-internal property of this single-account backend (ADR-005).

**Consequences:** Live verification: the exact crashing pattern (side query + agent turn fired in the same second against the real backend) now completes BOTH requests — 200 + structured tool_calls each, wall time = sum of the two turns (4.2 s), process alive. Offline tests prove max concurrency inside `chat_completion` is 1 and the gate survives mid-stream close from another thread. Suite 384 passed. Trade-off accepted: a long turn queues any concurrent request behind it; for a single-account DeepSeek Web backend that is correct behavior (the alternative was interpreter death), and Qwen Code tolerates the wait where it previously got a dead connection.

**Alternatives considered:** locking only the PoW solve (rejected — the shared `_parse_chunk` seam and general client state would still race); a pool of wasmtime solvers or per-request DeepSeekAPI instances (rejected — recompiles/instantiates the wasm module per request, more code, and the parser seam still needs serialization); fixing wasmtime/dsk upstream (out of reach — vendored and dormant; the gate solves it at the boundary); process-level request queuing in FastAPI (rejected — belongs to the backend that owns the unsafe state, keeps FakeBackend/tests unaffected).

## ADR-028 — M7 multi-turn tool loop: buffered tool turns, bounded repair, persistent tool-call ID index, lenient history validation

**Status:** Accepted (offline suite green + live probe PASSED 2026-08-15; M7 acceptance PASSED user-run 2026-08-15 after the ADR-029 hotfix — capture records 66–71)

**Context:** M6 acceptance PASSED (user-run, 2026-08-15): a live 7-call loop of sequential tool interactions through Qwen Code. The run also catalogued the wrinkles M7 must absorb: (a) the model occasionally answers a `tool_choice: "required"` turn in plain text, or malforms the control envelope (bad JSON, unknown tool name, truncated envelope) — M6's honest fallback then flushes raw sentinel text to the client as assistant content, degrading the agent loop; (b) TOOL_CALLING_PROTOCOL.md explicitly prescribes the remedy — "perform one bounded repair turn telling the model the call is invalid and listing valid tool names", "Avoid infinite repair loops", "If repair fails, use a bounded model repair turn or controlled error"; (c) ROADMAP M7 additionally requires a persistent tool-call ID mapping, repeated tool-result/model cycles, streaming tool-control buffering, and history validation. Constraints carried forward: canonical state is the truth (master prompt, ADR-020); the gateway never fabricates tool calls (ADR-023); only current-inference output is envelope-parsed (injection boundary); the Qwen Code client keys retries off HTTP status (docs/UPSTREAM_NOTES.md); every DeepSeekWebBackend call serializes through the ADR-027 call gate.

**Decision:** Five interlocking rules, implemented in app/server.py, app/conversation.py, app/tool_envelope.py:

1. **Buffered tool turns.** Every tool-ENABLED turn (both response modes) is drained through the envelope parser completely — per attempt — BEFORE any response byte is committed. The final outcome is re-emitted as synthesized normalized events (MessageStarted / TextDelta\* / ToolCallEmitted? / MessageFinished) through the UNCHANGED `sse_stream`, so the public chunk shapes stay byte-compatible with M6. Consequences: every failure of a tool-enabled turn now happens pre-response and answers with a real HTTP status (never an in-stream error envelope — better for client retry keying); an envelope can never leak partially because nothing is exposed before classification; tool-DISABLED streaming stays on the exact M3 path (byte-identical, M3 fixtures pinned). Accepted trade-off: first-byte latency of tool-enabled turns grows to the full turn length (tool turns are short in practice — one tool decision — and correctness wins; the master prompt's "buffer enough to classify and validate before exposing" is satisfied in the strongest form).
2. **Bounded repair policy.** `MAX_TOOL_REPAIR_ATTEMPTS = 1` — at most ONE repair retry, i.e. at most two backend calls per turn. Trigger: the attempt produced no valid tool call AND (`tool_choice == "required"` OR the parser's new `invalid_envelope_seen` flag is set — an invalid-region flush or a truncated envelope, i.e. the model clearly TRIED to use the format). The retry reuses the same compiled prompt plus a STATIC, deterministic repair hint appended after the tool instructions; the hint lists the valid tool names (client-supplied data) but NEVER echoes model output back into the prompt (injection boundary: model output is untrusted input; echoing it would amplify injections and make the retry non-deterministic). The retry reuses the same backend session but the SAME ORIGINAL `parent_message_id` — it re-branches from the pre-turn point, so the failed attempt never enters the threaded upstream context.
3. **Link invalidation after multi-attempt turns.** After ANY turn that used more than one attempt — whether the final attempt succeeded or fell back to honest text — the turn's final result is committed to canonical history FIRST, then the backend link (session + parent) is invalidated. Rationale: the upstream session now contains an orphaned attempt-1 branch that canonical history does not mirror; a later delta turn would silently diverge from canonical. Invalidation makes the NEXT request rebuild from canonical history (full prompt, fresh session — always correct, ADR-020 self-healing). Repair is rare (only on model misbehavior), so the occasional rebuild cost is acceptable; single-attempt turns keep the M6 behavior exactly (link intact, delta reuse).
4. **Persistent tool-call ID index.** `tool_call_index(messages) -> dict[id, CanonicalToolCall]` is promoted to app/conversation.py (first occurrence wins, deterministic). `_prepare_turn`'s known-tool-name seeding now uses it, and it backs history validation. The index is DERIVED from canonical history per request — it persists across turns, survives LRU eviction and restarts because the client re-sends full history — deliberately NOT a separate mutable registry (that would duplicate canonical state and violate "canonical history is the truth").
5. **Lenient history validation.** `validate_tool_history(messages) -> ToolHistoryFindings` reports orphan tool results (role=tool whose tool_call_id matches no assistant tool call in the history) and tool messages with a missing/empty tool_call_id. Policy is LENIENT (ADR-023 lenient-in): findings never reject a request; the history compiles as-is (orphan results already render with tool name "unknown", ids preserved verbatim) and the server logs a minimal warning (counts + capped id list, never message content — credentials rule). The HTTP surface already 400s a missing tool_call_id at canonicalization (UNSUPPORTED_MESSAGE), so this is defense-in-depth + operator observability for the canonical-state layer.

Supporting change: `EnvelopeParser` gains the read-only `invalid_envelope_seen` flag (set on an invalid-region flush in `feed()` and on a truncated-envelope flush in `finalize()`; never set by plain held-back text or after a valid emission).

**Consequences:** The M6 semantics change in exactly one visible way, as the protocol prescribes: an unknown-tool or malformed envelope now triggers one repair attempt before falling back to honest text (tests/test*m6_api.py's unknown-tool test updated to the repair-then-fallback semantics; two M5-era `tool_choice: "required"` fixtures likewise updated — the scripted plain-text model now costs two backend calls). Offline suite: 384 → 410 passed, 3 deselected (tests/test_m7_loop.py: tool-call index, lenient validation, invalid-envelope flag, bounded repair policy incl. link invalidation + rebuild + repair-failure HTTP status, buffered streaming chunk shapes, the 3-cycle multi-turn loop through the real app, lenient history logging). Live probe (2026-08-15, real DeepSeek backend through the full pipeline, streamed): THREE sequential tool interactions on the first try — `list_directory(docs)` → `read_file(docs/ROADMAP.md)` → `read_file(docs/TOOL_CALLING_PROTOCOL.md)` → final answer (`stop`), 13.5 s total, three unique gateway-minted `call_dsqg*`ids round-tripping verbatim through`role=tool.tool_call_id`, all tool turns `finish_reason: tool_calls`, every continuation on the session-reuse/delta path. The model followed the envelope protocol first-try on every turn, so no repair was triggered live (repair cannot be forced reliably against a cooperating model — it is covered offline; the probe script was deleted after use per the established pattern). The multi-cycle loop (≥3 sequential tool interactions + final answer) gains an offline integration test through the real app with FakeBackend; the M6 live acceptance already proved the loop end-to-end with Qwen Code itself.

**Alternatives considered:** unbounded or eager repair loops (rejected — protocol forbids infinite repair; one retry is the documented bound); echoing the model's malformed output back into the repair prompt (rejected — injection amplification, non-determinism; a static hint with the valid tool names is sufficient and safe); keeping incremental streaming for tool turns and repairing after the fact (rejected — already-streamed text cannot be un-sent; repair must decide before any byte); chaining the repair attempt after the failed one (parent = attempt-1 message id) instead of re-branching on the original parent (rejected — keeps the failed output out of the threaded context, and the link is invalidated afterwards anyway); strict history validation that rejects orphan tool results (rejected — ADR-023 lenient-in: the client's re-sent history is the truth, compile as-is and log); a stored per-conversation tool-call registry (rejected — duplicates canonical history; derive-on-request is simpler and self-heals after eviction/restart).

## ADR-029 — M7 acceptance blocker: prose-simulated tool use — anti-simulation instructions + pre-loop plain-text repair

**Status:** Accepted (written design-first after the live diagnosis; consequences updated after the offline suite + live re-verification; the fix unblocked the M7 acceptance re-run — PASSED user-run 2026-08-15, first try, capture records 66–71)

**Context:** The user's first M7 acceptance attempt (2026-08-15) stalled on the very first agent turn. Diagnostics record 61 (69 tools, `tool_choice` absent, task "list docs/ then read ROADMAP.md and TOOL_CALLING_PROTOCOL.md") got NO tool-loop follow-up — the capture showed only side query + memory passes afterwards. A live replay of the exact captured request through the real backend reproduced it: `finish_reason: stop`, zero `tool_calls`, no envelope attempted; the model had answered in PROSE, narrating a simulated tool loop — "Saya akan menampilkan daftar file…" with a fabricated `docs/` listing (reassembled from the QWEN.md reading list inside the system prompt) and "read" summaries of files it never read. This is why the answer looked "strange": plausible-looking, tool-less, hallucinated. Two ADR-028-era gaps combined: (1) the optional instruction wording ("You may either answer normally or request exactly one tool call") never forbids SIMULATING tool execution in prose — a model without native function calling falls back to narrating actions; (2) the repair trigger (`required` OR `invalid_envelope_seen`) cannot fire here — Qwen Code agent turns carry no `tool_choice`, and a model that never attempts the envelope sets no flag. The same stochastic wrinkle appeared on the M6 acceptance's first turn (hallucinated shell block); M7's mission is to absorb exactly this.

**Decision:** Two complementary changes, both static and deterministic:

1. **Anti-simulation instructions** (app/tools.py, `build_tool_instructions`): the optional branch gains "If you need a tool to answer, you MUST request it with the control envelope — you cannot execute tools yourself; NEVER simulate or narrate tool execution in prose (no fabricated listings or results).", and the shared envelope rules gain "- Never describe a tool call in prose; either output a real envelope or answer normally." (applies to both branches). The `required` branch keeps its MUST wording untouched.
2. **Pre-loop plain-text repair** (app/server.py): the bounded-repair trigger widens to `no valid call AND (required OR invalid_envelope_seen OR pre_loop)`, where `pre_loop` = the request's canonical history contains NO assistant tool call yet (`tool_call_index` empty). Rationale: the pre-loop tool-enabled turn is exactly where acceptance blocks; once a loop exists (history carries tool calls), a text answer is presumed a legitimate FINAL answer and must NOT be repaired — repairing there would nudge the model toward another tool call and could break loop termination (final-answer turns also carry tools). The retry reuses the existing static hint (its optional closing already is the soft "If no tool is actually needed, answer normally") plus one added anti-simulation sentence; the ADR-028 machinery is unchanged — re-branch on the ORIGINAL parent_message_id, commit-then-invalidate after multi-attempt turns, ≤2 backend calls per turn. Accepted cost: pre-loop plain answers (a greeting first turn, background memory "dream" passes) pay one extra backend call and its latency.

**Consequences:** Offline suite 410 → 413 passed, 3 deselected: three new repair tests replace the old optional-plain-no-repair test (pre-loop plain text → one retry carrying the static hint + anti-simulation sentence → bounded honest fallback; pre-loop plain-then-envelope → `tool_calls` on the retry; mid-loop plain text → NO repair, one inference, delta-reuse link intact — the termination guard), the optional instruction wording gains an anti-simulation assertion, and nine M5/M6-era single-turn fixtures (test_api, test_api_streaming, test_m5_diagnostics, test_m5_wire_fixtures, test_m6_api) were re-scripted to the new two-call semantics of pre-loop plain turns. ## ADR-031 — M8 hotfix: bounded mid-loop repair when the OUTPUT simulates tool calls (internal-format imitation)

**Status:** Accepted (2026-08-15; implemented and live re-verified the same day — see PROGRESS.md; point 4, the termination guard, superseded by ADR-035 the same day)

**Context:** The M8 acceptance was attempted twice by the user and failed both times with the same shape. Capture evidence (records 73–80) plus two deterministic replays of the exact turn-2 request show: turn 1 (pre-loop) correctly emitted the control envelope and executed one real `read_file`; the turn-2 response was `finish_reason: stop` with 0 tool_calls and no sentinel anywhere — instead, prose that SIMULATES the entire remaining loop, written in the gateway's OWN internal prompt-compilation format (`[assistant tool call]` / `id:` / `tool:` / `arguments:` blocks followed by `[tool result]` blocks with fabricated file contents). The model imitated the block format it sees in the compiled history — the most tool-like pattern in its context — instead of following the sentinel instructions (format leakage). None of the existing repair triggers fired: agent turns carry no `tool_choice` (`required` false), no sentinel was attempted (`invalid_envelope_seen` false), and the history already holds a tool call (`pre_loop` false). ADR-029's termination guard therefore flushed the 32 KB simulation as the final answer and the loop ended after one real tool interaction; the fixture bug was never fixed. The guard exists for a real reason — final-answer turns also carry tools, and repairing every mid-loop text answer would break loop termination — so the fix must distinguish simulated tool use from a genuine final answer with a HIGH-PRECISION signal, not a linguistic heuristic.

**Decision:**

1. **Simulation markers are detected in the current inference OUTPUT only.** `app/tool_envelope.py` exports `SIMULATION_MARKERS` — the control start sentinel `<<<DSQG_TOOL_CALL>>>` appearing as data, and the prompt compiler's internal block header `[assistant tool call]`. `app/server.py`'s `_run_buffered_tool_turn` checks each attempt's ASSEMBLED flushed text (chunk-split-proof — a marker spanning two backend deltas still hits) and treats a hit as proof of prose-simulated tool use. Both markers are unambiguous "tool call requested" markers: a genuine final answer never contains them. Detection scope is exactly the injection boundary the parser already enforces — only the current inference output is scanned; compiled history and tool RESULTS are input and never inspected (the poisoned-result test stays green).
2. **Repair trigger extended** (app/server.py): `needs_repair = required OR invalid_envelope_seen OR simulation-marker-in-output OR pre_loop`. Everything else about the bounded repair policy is UNCHANGED: at most `MAX_TOOL_REPAIR_ATTEMPTS = 1` retry (≤2 backend calls per turn), the static deterministic hint (now also naming the forbidden internal blocks), re-branching the SAME ORIGINAL `parent_message_id`, and commit-then-invalidate after multi-attempt turns.
3. **Anti-imitation wording** (app/tools.py + the repair hint): the instruction block states explicitly that `[assistant tool call]` / `[tool result]` blocks visible in context are conversation HISTORY data and must never be output, and that the envelope is the ONLY way to request a tool; the repair hint repeats this on the retry, since that retry is most often triggered by exactly this imitation.
4. **The termination guard stays pinned**: a mid-loop text answer WITHOUT simulation markers is still presumed the legitimate final answer and is never repaired.

**Consequences:** The dominant M8 failure mode gets one bounded steering retry per turn instead of silently ending the loop; when the retry emits a real envelope, the simulation never reaches canonical history or the upstream thread (re-branch + link invalidation, ADR-028 points 2–3). Worst case — the model simulates twice — costs one extra backend call and still flushes honestly. False positives (a genuine answer quoting an internal marker) cost one bounded retry and then flush honestly; acceptable precision trade-off for a marker set this specific. Offline tests pin all four branches: marker → repair → envelope recovery, marker twice → bounded honest flush, marker-less mid-loop text → NO repair (guard), and output-only detection scope. The protocol doc's "Simulated tool use" section documents the marker exception. Suite grows from 416.

**Alternatives considered:** PARSING the internal `[assistant tool call]` blocks into real tool calls (rejected — makes the leaked format a second protocol, rewards the imitation, widens the injection surface, and treats unversioned prose as wire data; strict-out per ADR-023); hiding or re-formatting the internal blocks in compiled prompts so the model cannot imitate them (rejected for this hotfix — the block rendering is pinned by M2–M7 fixtures and two accepted live runs, and the blast radius is too large for a hotfix; may be revisited if live evidence demands it); raising `MAX_TOOL_REPAIR_ATTEMPTS` (rejected — the bound is a protocol guarantee, and the problem is steering, not budget); escalating to `tool_choice: required` on mid-loop retries (rejected — the gateway never fabricates client intent, ADR-023).

## ADR-032 — M8 hotfix escalation: retry-scoped history annotation to break internal-format imitation

**Status:** Accepted, SUPERSEDED by ADR-033 (2026-08-15; implemented and live re-verified the same day — the replay proved the retry fires but the model copied the ANNOTATED header verbatim, so the annotation steers nothing; the annotation mechanism was reverted when ADR-033 landed)

**Context:** ADR-031's marker detection + bounded repair worked EXACTLY as designed — the gateway log for the exact replayed M8 turn-2 request shows `tool repair retry 1/1 (triggers: simulation_marker)` followed by `tool-enabled turn ends after 2 attempt(s); repair budget exhausted (triggers: simulation_marker)` — but the model simulated on BOTH attempts. ## ADR-033 — M8 hotfix escalation 2: stripped tool history in the simulation-triggered retry base

**Status:** Accepted (2026-08-15; superseded ADR-032's annotation mechanism the same day after live evidence falsified it)

**Context:** ADR-032's annotated retry base was implemented and re-verified live against the exact replayed M8 turn-2 request (capture record 75) — and falsified as sufficient. The gateway log shows `tool repair retry 1/1 (triggers: simulation_marker)` and a second attempt triggering `invalid_envelope_seen, simulation_marker`; the flushed retry output copied the ANNOTATED header VERBATIM (`[assistant tool call (already executed — context only)]` + `id:` / `tool:` / `arguments:` + a simulated `[tool result ...`). The model does not read annotations — it imitates whatever block format its context shows, header text included. Instruction-level steering (hints, header annotations) cannot overcome the few-shot pull. Within the hotfix envelope one lever remains: remove the template from the retry context entirely. The causal evidence still holds: pre-loop turn 1 — text blocks + tool instructions, NO tool blocks — is the shape that reliably emits envelopes in every captured attempt.

**Decision:**

1. **The simulation-triggered retry base is a STRIPPED compilation** (app/server.py `_prepare_turn` + `_strip_tool_history`): every tool-shaped message is omitted — tool-call-only assistant messages drop out, assistant messages with BOTH text and tool_calls keep their text, `role=tool` results drop out. Text blocks, the tool-instructions block and the repair hint remain. If stripping leaves nothing, the retry falls back to the original prompt. The MAIN path stays byte-identical (all M2–M7 fixtures pinned), and retries triggered by `required` / `invalid_envelope_seen` / `pre_loop` WITHOUT a simulation marker keep the original prompt verbatim (ADR-032 point 2 wiring, M7 repair assertions unchanged).

3. **The repair hint's simulated closing gains one sentence**: earlier tool results are not repeated in the retry; if the model still needs one, it re-requests the call with the envelope.
4. Budget (1 retry), re-branching the same original `parent_message_id`, commit-then-invalidate after multi-attempt turns, output-only marker detection, honest flush after exhaustion and the termination guard are all unchanged from ADR-028/029/031/032.

**Consequences:** The retry context presents ZERO imitable templates — it is exactly the empirically reliable turn-1 shape. Cost: the retry inference temporarily loses tool-result content; if the model still needs it, it re-requests the call and the client re-delivers the result next turn — canonical history never loses anything, because stripping happens only in the RETRY branch prompt, which the re-branch + link invalidation discards anyway. Offline tests pin: stripped retry recovers a real envelope, stripped retry after exhaustion stays honest, non-simulation retries keep the plain prompt, and the termination guard. If live evidence STILL shows simulation on the stripped shape, the recorded next escalation is a MAIN-path format change rendering historical tool calls in the ENVELOPE format itself — turning imitation into correct behavior — deferred because it breaks pinned M2–M7 fixtures and needs its own acceptance.

**Alternatives considered:** keeping the annotation AND raising the budget (rejected — attempt 2 proved the annotation is ignored; another sample of a failing shape is not a shape change); main-path format change NOW (deferred again — largest blast radius in the codebase; the stripped retry is smaller, scoped to the failing branch, and directly evidenced by the turn-1 shape); parsing simulated blocks into real calls (rejected in ADR-031, unchanged).

## ADR-034 — M8 hotfix escalation 3: main-path history tool calls render as the instructed envelope itself (imitation becomes a VALID tool request)

**Status:** Accepted (2026-08-15; implemented and live re-verified the same day — replay of capture record 91, the turn the third acceptance died on, recovered a REAL tool call; complementary escalation recorded as ADR-035)

**Context:** The user's THIRD M8 acceptance attempt (2026-08-15 ~10:38) failed again, and the turn-by-turn reconstruction from the gateway log plus capture records 88–92 showed every hotfix mechanism working as designed — while the model produced a NEW failure shape escaping all detectors. Turn 1 (pre-loop) simulated and recovered via the ADR-029 retry. Turn 2: attempt 1 simulated → ADR-033 stripped retry recovered, but re-read a file already read (the stripped base loses "already read" context; the client de-duplicated gracefully). The causal chain from ADR-032/033 is now fully evidenced: the model ignores annotations and imitates whatever block format its context shows; removing the template from the RETRY works but degrades the retry's information (duplicate reads). The escalation ADR-033 explicitly recorded — a MAIN-path format change rendering historical tool calls in the ENVELOPE format itself — is the remaining lever: if the context's most tool-like pattern IS the instructed envelope, imitation becomes a valid tool request instead of a failure mode.

**Consequences:** The main-path prompt format for tool-shaped history changed — the M5 wire-fixture row `tool_history_turn` and the prompt-compiler history tests were re-pinned to the envelope block (documented in the fixture README). ## ADR-035 — M8 hotfix escalation 4: universal bounded repair — every envelope-less tool-enabled turn gets ONE retry (termination guard removed)

**Status:** Accepted (2026-08-15; implemented and live re-verified the same day; supersedes ADR-031 point 4 and the termination-guard clauses carried by ADR-029/032/033)

**Context:** ADR-034's live verification replayed capture record 90 — turn 2 of the failed acceptance, the turn whose stripped-retry recovery had re-read a file — against the rebuilt gateway: HTTP 200, `finish_reason: stop`, 0 tool_calls, content "I'll read the test file and then run the tests to find the bug." Marker-less mid-loop prose. The termination guard flushes exactly this shape as the final answer, so the loop would still die at turn 2. The guard's premise — "marker-less mid-loop text is presumed the legitimate final answer" — is now falsified three times over (records 75, 91-attempt-2, and 90): mid-loop turns keep emitting marker-less INTENT statements instead of envelopes, and in the 10:38 run all three mid-loop turns were non-envelope on attempt 1. The guard was protecting loop termination, but termination does not actually depend on it.

**Decision:**

1. **Universal bounded repair** (app/server.py `_run_buffered_tool_turn`): EVERY attempt that produced no valid tool call is retried while budget remains — the `not reasons` short-circuit is gone. No unbounded loop exists: every tool-enabled turn terminates after at most two attempts.
3. **Retry-base branching unchanged** (ADR-033): simulation-marker retries rebuild on the stripped base; every other retry — including `no_envelope` — keeps the ORIGINAL prompt with full history, so the repaired turn makes informed calls (no duplicate reads) instead of re-deriving context.

**Consequences:** Every genuine final answer on a tool-enabled turn pays ONE extra backend call (bounded latency; content unchanged — attempt 2 repeats and flushes). **Alternatives considered:** a linguistic heuristic for intent statements ("I'll read..." → repair) (rejected — fragile, untestable, violates ADR-031's high-precision-signal principle); raising the budget above 1 (rejected — the bound is a protocol guarantee, and one retry under this policy already converts every observed failure shape); keeping the guard and relying on stochasticity (rejected — the record-90 replay shows the loop dying at turn 2; the user had already failed the acceptance three times); making the retry hint REQUIRED for no_envelope turns (rejected — that would coerce tool calls from genuine final answers and re-create the termination risk the hint's plain-answer closing exists to remove).

## ADR-036 — M9 reliability hardening: bounded transport retry + upstream timeout + strict terminal enforcement + public metrics

**Status:** Accepted (M9 design gate; 2026-08-15)

**Context:** M9 (00*MASTER_PROMPT roadmap) demands that \_simulated failures produce deterministic public behavior and no hot/infinite retry loop exists*. Audit of the M8-era code against each M9 item:

1. **Retry policy:** no gateway-level retry exists anywhere; every transient `BackendFailure` maps straight to a 4xx/5xx (the Qwen Code SDK retries 429 itself, per its log `Retrying in 1s ... attempt 1/3`). The taxonomy already carries a per-failure `retryable` flag with a sound `DEFAULT_RETRYABLE` table (RATE_LIMITED / UPSTREAM_NETWORK / UPSTREAM_5XX = retryable; AUTH_INVALID / CLOUDFLARE_BLOCKED / UPSTREAM_PROTOCOL / CLIENT_BAD_REQUEST / INTERNAL = not).
2. **Timeout:** the vendored client passes `timeout=None` on BOTH HTTP calls (`_make_request` and `chat_completion`) — a dead upstream socket can block the single call-gate slot FOREVER (ADR-027 serializes all backend calls), wedging the entire gateway. `curl_cffi` semantics (audited in `curl_cffi/requests/utils.py:796-816`): a float timeout with `stream=True` maps to `CONNECTTIMEOUT_MS` + `LOW_SPEED_LIMIT=1` / `LOW_SPEED_TIME=ceil(timeout)` — an INACTIVITY/STALL timeout that survives healthy long streams but aborts silent sockets; without streaming it maps to a total `TIMEOUT_MS`. One injected float therefore gives the right semantics on both vendored call sites. Timeouts surface as `RequestsError` → vendored `NetworkError` → `UPSTREAM_NETWORK` → retryable.
3. **Cancellation:** true upstream cancellation is impossible without deadlock risk: the ADR-027 `Semaphore(1)` gate is held across the generator's yields, so an abandoned mid-stream thread may never reach the `finally` release and would deadlock every subsequent backend call. The timeout of item 2 is the bounded substitute; client-disconnect semantics stay as documented in M3 (orphan turn runs to completion in the threadpool; nothing to roll back on a sessionless backend).
4. **Malformed/truncated streams:** mid-stream exceptions already close with an error envelope and NO `[DONE]` (ADR-011/019). But a stream that ends CLEANLY without ever carrying a terminal marker is silently "completed": `sse_stream` yields `[DONE]` regardless, and the non-stream/buffered paths fabricate `finish_reason="stop"` via `STREAM_EMPTY` fallback. A truncated DeepSeek stream would hand Qwen Code a plausible-but-incomplete final answer.
5. **Cloudflare normalization:** already mapped twice (explicit `CloudflareError`; `APIError` whose message contains "cloudflare") to CLOUDFLARE_BLOCKED → 503, non-retryable — but pinned by NO test.
6. **Strict terminal/finish:** finish reasons are always mapped to a non-null OpenAI value (M2), and `[DONE]` is success-only; the gap is item 4's missing-terminal case.
7. **Metrics/logging:** none exist — no counters, no latency, no retry log lines.

**Decision:**

1. **Bounded transport retry** (new `app/reliability.py::with_transport_retry`): wraps any zero-arg callable that raises `BackendFailure`. Policy: on a failure with `failure.retryable` truthy AND attempts remaining, sleep `backoff_seconds * attempt_number` (linear, deterministic — no jitter: local-first single-client gateway, deterministic tests are worth more than decorrelation), then re-run. Anything non-retryable, or the final retryable failure, re-raises unchanged (the existing error*mapping layer then produces the exact same HTTP status as before — \_failure behavior is unchanged, only latency before it*). Config: `GATEWAY_MAX_RETRIES` (default **2** → at most 3 attempts per request; worst case bounded by 0.5s + 1.0s of backoff), `GATEWAY_RETRY_BACKOFF_SECONDS` (default **0.5**). Injectable `sleep` and `on_retry` callback make tests deterministic and give the server its log line (`transport retry %d/%d after %ss: category=%s`) and metrics increment. Retry wraps EXACTLY the pre-byte backend interactions: (a) streaming-priming closure (session + stream_turn + first event), (b) each attempt inside `_run_buffered_tool_turn` (the drain; repair retries and transport retries compose — repair is semantic, transport is transient), (c) `create_session` at session resolution. Mid-stream failures (after HTTP 200 committed) are NEVER retried — the stream is closed with the error envelope as today; retrying would replay deltas into a committed stream. A retried attempt is a full re-issue of the same prompt on the same session/parent (idempotent from the client's viewpoint; upstream may record a duplicate message branch — the same accepted cost as ADR-028's repair re-branching, and bounded by the budget).
2. **Upstream timeout** (annotated vendor patch, `[DSQG-VENDOR-PATCH]` precedent from the pkg_resources fix): both `timeout=None` sites read a module-level `dsk.api.DEFAULT_REQUEST_TIMEOUT` instead; `DeepSeekWebBackend.__init__` sets it from `DSQG_UPSTREAM_TIMEOUT_SECONDS` (default **60.0**, float). Per curl_cffi semantics this is a stall timeout on the streaming call (healthy multi-minute thinking streams survive; a silent socket aborts after 60 s) and a total timeout on control-plane calls (session create, PoW fetch — both sub-second when healthy).
3. **Strict terminal enforcement** (server-level, both response modes): a consumed turn that never produced `MessageFinished` is a truncation failure — `BackendFailure(UPSTREAM_PROTOCOL, "…ended without terminal marker…", retryable=True)` (transient truncation deserves one bounded retry; a persistent one surfaces as 502). Non-stream/buffered modes raise it pre-byte → HTTP status (+ transport retry). Streaming mode detects it at iterator exhaustion in `sse_stream` and emits the error envelope WITHOUT `[DONE]` (same mid-stream failure contract). `STREAM_EMPTY`'s degenerate clean-completion rendering becomes unreachable via the routes (the primed first event IS the terminal marker for a truly empty-but-complete turn); the sentinel stays only as the module-level defensive shape.
4. **Cloudflare pins:** regression tests pin BOTH classification paths to CLOUDFLARE_BLOCKED / 503 / `upstream_unavailable_error` type / non-retryable → guaranteed no retry loop (transport retry must not fire; attempt count == 1).
5. **Metrics** (new `app/metrics.py::MetricsCollector`, thread-safe via one lock): counters — requests by endpoint + status class, backend attempts, backend failures by category, transport retries, tool turns, tool-repair retries, tool-repair budget exhaustions; duration summary (count/sum/max) for full backend attempts. Exposed at **GET /admin/metrics** (JSON; unauthenticated like /health — local-first gateway, no secrets in the payload). `create_app` gains an optional `metrics` parameter; every request path increments it in finally blocks so failures count too. Log lines: the retry line of item 1 plus a per-request completion line (method, path, status, duration).
6. **Compatibility regression suite:** new `tests/test_m9_reliability.py` (FakeBackend scripted failures — the fake backend already supports `BackendFailure` instances in turn scripts): retryable → success after retry (attempt counts asserted via `turn_calls`); non-retryable → immediate mapped error, exactly 1 attempt; budget exhaustion → mapped error after max_retries+1 attempts with the recorded sleep sequence [0.5, 1.0]; truncation → deterministic UPSTREAM_PROTOCOL + retry recovers a healthy second attempt; mid-stream truncation → error envelope, no `[DONE]`, no retry; Cloudflare pins; metrics shape + counters; /admin/metrics route. Existing scripted turns that lack a terminal marker are re-pinned to the new truncation behavior (audited during implementation; the module-level `sse_stream` degenerate-path tests remain valid as direct unit tests).

**Consequences:** Every transient upstream hiccup (rate limit window, socket stall, truncated stream) gets up to 2 automatic bounded retries before the SDK's own retry logic even sees a status — total worst-case extra latency 1.5 s (configurable, never unbounded: every loop has a literal numeric budget). Dead sockets can no longer wedge the call gate (60 s stall cap). Qwen Code can never again receive a `[DONE]`-sealed stream that lacked a real upstream terminal. `/admin/metrics` gives the operator the first quantitative view of gateway behavior (and a live acceptance evidence source for later milestones). Suite grows beyond 424 tests; the only behavior changes are (a) retryable failures may now succeed transparently or arrive ~1.5 s later with the same status, and (b) clean-but-markerless streams become 502/error-envelope instead of a fabricated `stop` — both strictly closer to upstream truth. The vendored patch is annotated and confined to the two timeout literals.

**Alternatives considered:** true client-disconnect cancellation of the upstream stream (rejected — call-gate deadlock risk documented above; timeout bounds the exposure instead); exponential backoff with jitter (rejected — deterministic linear schedule preferred for a single-client local gateway and exact test pins); gateway retry on mid-stream failures (rejected — would duplicate deltas into a committed HTTP 200 stream); making truncation non-retryable (rejected — a one-shot reconnect recovers the dominant real-world cause, and the budget keeps the worst case bounded); raising transport retries above 2 (rejected — the SDK already retries 429/timeout-class statuses 3×; compounding budgets beyond this turns a genuinely down upstream into a multi-minute stall); authenticated /admin/metrics (rejected — no secrets exposed, /health precedent, local-first posture).

## ADR-037 — M10 multi-account router: in-memory account registry, health states, sticky conversations, least-active selection, 401/429 account consequences

**Status:** Accepted (M10 design gate; 2026-08-15)

**Context:** M10 (00_MASTER_PROMPT roadmap) demands: an account table; encrypted credentials; healthy/cooldown/invalid/disabled states; sticky conversation account; least-active/healthy routing; 401 invalidation; 429 cooldown. Exit: _new conversations avoid unhealthy accounts; healthy existing sessions stay sticky._ Audit of the M9-era code against each item:

1. **Single-account today:** `create_app` holds ONE `LLMBackend` on `app.state.backend`; `Conversation.backend_account_id` already exists (ARCHITECTURE.md field list, ADR-020 schema) but is always `None`; `ConversationStore.commit_turn` never sets it. Config parses exactly one `DEEPSEEK_AUTH_TOKEN` into `DeepSeekWebSettings`.
2. **Per-account isolation is real:** each `DeepSeekWebBackend` owns its own `DeepSeekAPI` → its own `DeepSeekPOW` (wasmtime Engine/Store/Instance built inside `DeepSeekPOW.__init__`, `vendor/deepseek4free/dsk/pow.py:21-39`) and its own ADR-027 call gate. The ADR-027 wasmtime corruption mode is same-solver-only, so N accounts = N independent serialization domains; cross-account concurrency is safe and single-flight becomes PER-ACCOUNT.
3. **M9 defines "final":** `with_transport_retry` already absorbs transient failures inside a bounded budget. Account-level consequences must attach ONLY to the FINAL surfaced failure — punishing an account per attempt would bench it on the first retryable 429 that the budget then recovers.
4. **Storage precedent:** ADR-020 keeps ALL state in-memory (SQLite deferred with the storage milestone). The account table follows suit; with nothing written to disk, "encrypted credentials" has no at-rest surface yet. docs/SECURITY.md explicitly permits environment-only credential loading before persistence and prescribes the master-key design for when persistence arrives.
5. **Taxonomy ready:** `AUTH_INVALID` (non-retryable, single attempt) and `RATE_LIMITED` (retryable) already carry exactly the 401/429 semantics; `error_mapping` already turns them into 502/429.
6. **Sticky rule:** ARCHITECTURE.md — "a conversation should normally remain on the account that created its backend session. Do not round-robin every turn."

**Decision:**

1. **New module `app/accounts.py`:** `AccountRecord` — the ARCHITECTURE.md accounts schema in-memory: `id`, `label`, `backend` (the account's `LLMBackend` instance), `enabled`, `health_status` ∈ {healthy, cooldown, invalid}, `cooldown_until`, `consecutive_failures`, `last_used_at`, `created_at`, `updated_at`. The record holds NO credential — the secret lives only inside the account's backend instance (`SecretStr` in `DeepSeekWebSettings` → token consumed at `DeepSeekWebBackend` construction), so every admin surface is masked by construction. `AccountRouter` (thread-safe, injectable clock):
   - `select_for_new_conversation(store)` — among USABLE accounts (enabled; healthy, or cooldown whose `cooldown_until` has passed — lazy promotion, no background thread), choose the minimum of `(active_conversations, last_used_at-or-0, config order)`; `active_conversations` counts stored conversations with `backend_account_id == id`, DERIVED from the store each call (self-healing like the tool-call index, ADR-028 — never drifts under LRU eviction the way a counter would). Zero usable accounts → `BackendFailure(RATE_LIMITED)` if any account is still in cooldown (429 → the client backs off; transient) else `BackendFailure(AUTH_INVALID)` (502 → operator action). Messages never contain secrets.
   - `record_success(account_id)` — state → healthy, cooldown cleared, `consecutive_failures = 0`, `last_used_at = now`.
   - `record_failure(account_id, category)` — `consecutive_failures += 1`; `AUTH_INVALID` → `health_status = invalid` AND invalidate the backend link of every conversation bound to that account (its next request rebuilds through the router onto a usable account — the existing ADR-020 rebuild path; no mid-conversation session migration, which is M11); `RATE_LIMITED` → `health_status = cooldown`, `cooldown_until = now + cooldown_seconds`; ALL OTHER categories → counter only (network/protocol failures are not evidence against the account).
   - `set_enabled(id, bool)` / `reset(id)` — operator lifecycle methods exist and are unit-tested, but get NO HTTP surface in M10 (account lifecycle management is M12). Disabling also invalidates the account's conversation links.
2. **Routing integration (server.py):** `_prepare_turn` becomes account-aware. STICKY: a matched conversation with a live backend link and a known account usable for sticky (enabled, not invalid — cooldown ALLOWED, see alternatives) keeps that account's backend. Otherwise (new conversation, invalidated link, unknown/invalid/disabled account) the router selects, `create_session` runs on the selected account's backend inside the existing M9 retry wrap, and a final `BackendFailure` there records the account outcome before re-raising. `_TurnContext` gains `account_id` + the selected backend (the route's stream calls switch from `app.state.backend` to the context's backend); `ConversationStore.commit_turn` gains an `account_id` keyword that persists the binding (schema + `to_dict` round-trip already exist). Consequences attach at the EXISTING final-failure sites (the `_invalidate_turn` call sites of all four response paths + `_observed_events`' mid-stream path) via one combined fail helper — no new failure semantics anywhere.
3. **Config (config.py), backward compatible:** `DEEPSEEK_AUTH_TOKEN` alone → ONE account with id `default`; zero behavior change (the entire 458-test suite is the regression pin). New `DSQG_ACCOUNT_TOKENS` (comma-separated) → N accounts `acct-1..N` in config order. Both variables set → `ConfigError` (ambiguous). Empty entries or duplicate tokens → `ConfigError` (messages name the variable, never a value). `DSQG_COOKIES_FILE` together with multi-account → `ConfigError`: cookies are per-account credentials and sharing one `cf_clearance` across tokens would be wrong; per-account cookies arrive with the persistence/admin milestones (fail closed, SECURITY.md). New `DSQG_ACCOUNT_COOLDOWN_SECONDS` (default **300**, must be > 0).
4. **Wiring:** `build_router(settings)` next to `build_backend`; `create_app(..., router=None)` — when no router is injected it wraps the (injected or built) single backend in a one-account router with id `default`, so every existing call site and test keeps working unchanged. Tests build multi-account routers directly from `FakeBackend` instances (the fake backend's `BackendFailure` scripting already covers 401/429 shapes). `app.state.router` is new; `app.state.backend` stays as the FIRST account's backend for compatibility.
5. **Observability:** **GET /admin/accounts** — read-only, unauthenticated (the /admin/metrics rationale: local bind, payload structurally secret-free). Per account: id, label, enabled, derived state (`disabled` > `invalid` > `cooldown` > `healthy`), `cooldown_remaining_seconds`, `consecutive_failures`, `active_conversations`, `last_used_at`. No mutation surface (M12). `/health` keeps its exact shape: `ok` = any enabled account not invalid (single account → identical to today).
6. **"Encrypted credentials" interpretation:** with storage in-memory-only there is nothing at rest to encrypt; credentials are held as `SecretStr` (masked in repr/JSON by construction), never logged (SECURITY.md logging policy unchanged), and never serialized by any endpoint. At-rest encryption (SECURITY.md's master-key design) is explicitly DEFERRED to the milestone that persists the account table — recorded here so the roadmap item is interpreted, not silently dropped.
7. **M11 boundary:** no mid-conversation session migration, no proactive failover orchestration, no failover metrics marker in M10. An existing conversation whose account dies simply loses its backend link and rebuilds on another account at its NEXT request through the ADR-020 path; M11 owns the named, observable failover event (rehydration semantics, tool-history/ID preservation audit, metrics marker).

**Consequences:** New conversations never land on a cooldown/invalid/disabled account (least-active among the usable ones; unused accounts first). Existing sessions on a healthy account are strictly sticky — no per-turn re-selection, no churn. A final 401 retires the account until operator action and releases its conversations to rebuild elsewhere; a final 429 benches the account from NEW conversations for a bounded, configurable window while its existing sessions keep working (the M9 retry budget absorbs the transient window first). Single-account deployments are byte-for-byte unchanged in behavior. New deterministic public failure: all accounts unusable → 429 (any cooling down) or 502 (none), message secret-free. Account state rebuilds from config on every restart (in-memory registry; a cooled-down/invalid account starts healthy again — acceptable for v1, persistence later). Multi-account is config-driven only; runtime add/remove is M12.

**Alternatives considered:** round-robin per turn (rejected — violates the ARCHITECTURE.md sticky rule; upstream sessions belong to one account); moving sticky sessions OFF a cooling-down account (rejected — cooldown is a transient rate-limit window, the upstream session stays valid, and moving would pay full-history rebuild prompts for no gain; only invalid/disabled releases links); account consequences per attempt instead of per final failure (rejected — the M9 budget recovers most transient 429s; per-attempt punishment would bench healthy accounts during normal operation); auto-invalidation after N consecutive non-auth failures (rejected for M10 — no evidence-based need yet; `consecutive_failures` is recorded so a future policy can act on it, and auto-invalidation during an upstream-wide outage would disable the whole fleet); encrypting credentials in RAM (rejected — the process itself needs plaintext to call upstream, so RAM encryption only defends against memory dumps while adding key management; SECURITY.md defers at-rest encryption to persistence); router-owned attempt execution (rejected — would entangle routing with the M6/M7 repair loops; attaching consequences at the existing final-failure/commit sites is minimal and keeps every pinned behavior intact); persisting the account table to SQLite now (rejected — ADR-020 precedent: the storage milestone is deferred, and account state reconstructs from config on restart).
